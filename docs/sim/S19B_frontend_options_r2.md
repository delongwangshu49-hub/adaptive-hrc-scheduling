# S19B 双语试用与演示工作台选型

2026-10-11；PR172。负责人明确日常开发试用用简体中文、课程展示用英语，操作与反馈要集中、清晰，同时保留Isaac真实场景及内部生产动作。当前 **TECHNOLOGY_SELECTION_PENDING / IMPLEMENTATION_NOT_STARTED**。按这些优先级，推荐调整为 **B 独立双语桌面工作台**；C本地浏览器工作台为次选，A定制Kit内工作台仍可选。当前只修订方案，推荐不代替负责人选择。

本版承接并调整[r1选型稿](S19B_frontend_options_r1.md)的使用体验重点与推荐；r1接口核查、版本候选、运行契约和性能边界继续适用，旧推荐按原时点保留。S19A已发布基线、几何/碰撞/路线/手位/工时/容量/人因及工业G2边界保持，新技术栈、B1/B2/B3制作和S20—S28尚未启动。

## 工作台应提供的体验

使用者从一个项目入口完成“准备订单/案例→检查输入→启动→查看场景与状态→处理可支持操作→查看结果和证据”。普通操作隐藏开发工具细节，运行身份、完整原因码、审计来源等保留在详情中。开发试用和演示使用同一套后端及规则；切语言或进入演示布局只改变显示，不能重启运行、修改参数、改变时钟或清除失败。

- 开发试用默认简中，顶部固定 `简体中文 / English` 切换；菜单、输入字段、校验提示、状态、等待/失败原因、确认对话框及证据摘要均提供两种语言。未知后端原因保留原码和“未解释”标记，不编造原因。输入的用户备注保持原文，不自动翻译。
- 主操作区围绕订单/案例、运行、状态、证据四个任务组织。高级配置和原始日志收在可展开详情中；演示布局突出订单状态、场景、当前动作和异常原因，诊断事实仍可查。
- 每项输入立即给字段校验；提交后区分“已提交/等待确认”“已接受”“已拒绝及原因”。订单行、状态和场景只依据后端确认同步，不因按钮点击就显示已经生效。
- 显示每个产品的当前工序、进行中动作、等待/失败原因及已完成事实，并可一键请求定位相关人物/设备。若显示总体进度，先定义分母和适用范围，不能用静态工序数量掩盖返修、模式分支或截尾。
- 数据陈旧或断连用显著文字和时间提示；正常、等待、失败不能只靠颜色区分。按钮说明当前能否操作及原因，不把暂停、停止、重置和关窗混在一个开关中。

这些是产品要求，三条路线均须满足，不能把双语解释为只翻译按钮。

## 三条路线按本轮要求重新比较

方案字母沿用r1，避免选择时混淆。复杂度与体验排序属于工程判断，不是已测工期或性能结论。

| 比较项 | A Kit内定制双语工作台 | B 独立双语桌面工作台 推荐 | C 本地浏览器双语工作台 |
| --- | --- | --- | --- |
| 技术 | 现有omni.ui3.3.1，轻启动器 | PySide6/Qt Widgets，受控运行桥接 | FastAPI/Uvicorn，HTML/CSS/JavaScript |
| 普通使用者面对的入口 | 项目专用面板与Kit场景 | 项目主窗口，直接启动CPU/Kit及查记录 | 本机页面，直接选案例及查记录 |
| 中英双语 | 自有词典更新项目控件，CJK字体/输入法须验证；不承诺整个Isaac编辑器汉化 | Qt翻译机制成熟，窗口/表单/状态可统一切换 | 自有中英词典更新页面，日期/数字按locale显示 |
| 信息输入与反馈 | 可重排为任务页，但复杂表格/提示仍要在Kit控件体系实现 | 订单表格、表单、状态列表、原因详情及本地证据适合集中管理 | 表单、状态卡片、筛选和演示布局灵活 |
| Isaac场景与动作 | 同一Kit窗口内显示，场景与操作结合最直接 | 保留独立Isaac场景窗口，与主控窗口并排协作 | 保留独立Isaac场景窗口，与页面并排协作 |
| CPU与历史记录 | 由轻启动器补入口，Kit未启动时功能较精简 | 无Kit时仍有完整主工作台 | 无Kit时仍有完整页面工作台 |
| 主要成本 | 定制布局/双语/字体，协调Kit计算与UI更新 | 新增Qt环境/打包，跨进程状态与双窗口同步 | 新增本机服务，连接/刷新/多标签及浏览器状态管理 |
| 更适合 | 最看重场景与控制同窗，接受保留Kit外壳 | 最看重便捷试用、订单输入和稳定的本地演示入口 | 最看重页面式信息布局和演示展示 |

### A 场景和操作集中在Kit内

这条路线需要重做项目专用工作区，把现有琐碎按钮整理成“准备、运行、诊断、证据”任务页。自有面板可以设计中英文字典和语言切换；现有英文按钮是当前脚本的写法，不能推导为omni.ui只能做英文。中文字体、输入法、表格和英语长文本适配均须在本机原型实测。Kit外壳及高级工具不承诺全部汉化。

利用可停靠窗口，将普通工作区与既有视口放在一起，尽量减少操作者进入USD属性或开发菜单的需要。[omni.ui Window能力](https://docs.omniverse.nvidia.com/kit/docs/omni.ui/3.3.1/omni.ui/omni.ui.Window.html)只支持实现可能性，实际简化和中文渲染尚未制作/验证。

### B 用专用桌面工作台完成试用和演示

主窗口统一订单/案例输入、运行状态、系统反馈、证据和语言切换；Isaac作为真实生产显示后端保留。拟采用主控窗口与场景窗口并排的日常布局，并验证启动后窗口协调、显示焦点及实体定位；不是把Kit渲染替换成另一套模型，也不承诺首版嵌入Kit窗口。

Qt的 `QTranslator` 与 `LanguageChange` 机制支持运行时更新界面文本；PySide6官方提供翻译流程。词典、后端原因码解释、动态状态和界面重翻译仍须项目实现并测试。[PySide6翻译指南](https://doc.qt.io/qtforpython-6/tutorials/basictutorial/translations.html)、[Qt动态语言切换](https://doc.qt.io/qt-6/i18n-source-translation.html#prepare-for-dynamic-language-changes)

推荐B是因为本轮重点已明确为小组实际试用、信息输入、清楚反馈和方便演示。完整独立工作台能把这些操作统一组织，不必日常依赖Kit编辑器的菜单体系；项目后端以Python为主，桌面运行桥接可沿用同类技术。代价是Qt依赖、打包和两个窗口的协调。候选PySide6版本及隔离要求沿用r1，当前不安装。

### C 用本机网页工作台完成输入和展示

页面承担订单/案例编辑、状态卡片、等待原因、记录和语言切换。拟用自有中英词典翻译业务文案；浏览器 `Intl`负责日期/数字等格式，不会自动翻译业务提示。[ECMAScript国际化规范](https://tc39.es/ecma402/#intl-object)

这条路线适合页面式布局与检索，英文演示可以保留更大的状态概览。Isaac仍通过本机桥接实际运行和渲染，首版场景显示在独立Kit窗口；浏览器页与场景窗口并排，不承诺在网页内直接显示实时三维。若要把真实Kit画面嵌入网页，就涉及流媒体及额外延迟/依赖验证，超出当前首版路线，不能用静态截图冒充。

本机单操作者与单一后端事实保持，多个页面也须共享同一控制锁；不将“小组成员可使用”解释为已授权远程多人协同。框架、版本候选及HTTP/连接验证范围沿用r1。

## 订单输入的真实能力范围

订单编辑应纳入工作台规划，同时明确界面字段与执行能力的对应关系。

| 情况 | 拟议处理 | 现有接口核查 |
| --- | --- | --- |
| 运行前新增/修改草稿 | 选择受支持产品/案例、数量及释放时间，校验后生成配置摘要，再创建新运行；草稿删除不等于生产取消 | 现有见证CLI支持1—3产品、SR-W1或SR-W2及release-times；每个运行使用单一variant，组合还须通过既有场景规则 |
| 运行中输入新需求 | 先保存待处理草稿或显示尚未支持，不能仅增加表格行就算已进入调度 | Configuration在启动时构建；ORDER_ARRIVAL释放已在配置中的产品，不是任意新订单接入服务 |
| 运行中改已有订单 | 分清未释放、未开始、在制和已承诺的修改，必须保留已执行/资源持有事实并由后端决定接受范围 | 当前未有通用订单修改端到端入口；修改工艺/容量/人因等冻结值不随输入界面放开 |
| 运行中取消 | 作为生产处置请求，明确库存/在制/READY等边界并保留回执/证据 | 已有有限取消见证不等于通用交互取消已开放，需映射已批准通道并验证 |

运行前编辑是首版可行的最小输入路径，但界面本身仍待制作。运行中插单/改单作为明确待核查需求保留；若后续要做，应先定义订单变更契约、准入、规划观察、缓存/承诺、实际USD实体与证据迁移影响，再决定具体实现范围。此次偏好澄清不提前授权这些后端扩展。

## 双语与反馈验收要求

拟采用稳定的语言无关状态/原因码，前端以 `zh-CN/en` 显示解释。源记录、配置摘要、实体ID、运行ID和审计码不随语言改变；专业术语需建立中英对照，如Order/Product、Running/Waiting/Failed、Stop/Reset，避免两种语言表达不同控制语义。中文备注用UTF-8保存；英语演示语言选择保持到下一次打开，语言偏好不作为生产参数。

语言切换必须保留未提交草稿、当前运行、选择实体、已确认请求和记录位置，不补发命令、不触发重置。普通状态提示用简短自然语言，细节保留参数、原因码、发生时间和证据链接；未得到执行确认时写“等待后端确认”，不能翻译成“操作成功”。

原型与B1须检查CJK缺字、输入法、英文长句/按钮溢出、中文表单、错误提示、两语言术语一致、键盘导航、缩放以及仅语言切换时生产摘要不变。B2验证双语输入与运行契约，B3由负责人以简中完成试用任务，再切英语完成同一条演示路径，人工体验不能由AI代填。

## 选定后的工作顺序提示

1. **负责人选路线**：A、B或C；仍未默认选择。视觉风格在此后单独确定。
2. **最小纵向原型**：一例CPU、一例真实Kit、一个历史记录；中英切换、运行前订单/案例草稿、清楚状态与实际场景连接。先验证中文字体/输入法、语言切换不改运行、UI不阻塞生产和双窗口或同窗体验，再确认布局。
3. **B1信息审查**：双语只读状态、订单/实体定位、等待/失败解释、新鲜度、记录/证据入口；观察隔离保持。
4. **B2最小控制**：真实贯通输入校验、启动、有序停止、请求确认/幂等和断连重连；暂停/继续/重置及运行中订单操作仅在对应后端能力实际通过后开放。
5. **B3实际试用和演示**：负责人完成“编辑受支持订单/选案例→试跑→看真实场景与动作→查等待/故障→停止/受支持重置→看证据”，切英语再检查演示路径；保留不支持或失败的实际阻断。
6. **语义和性能对照及收尾**：前端开关、规定生产负载、中文/英文同任务及显示方式成本单列验证，全部原预算/保护/日志精度保持；形成确切成果包，再实际验收与批准发布。S20另行启动。

顺序中的动作均尚未实施；本版不承诺未经测量的工期、中文Kit全编辑器本地化、嵌入渲染或运行中任意订单变更。只在负责人选定路线后继续制作。
