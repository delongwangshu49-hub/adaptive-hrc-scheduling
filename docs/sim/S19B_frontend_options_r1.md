## 三个可选择方案

### A Isaac原生面板与小型本地启动器

沿用当前Kit/Python，使用 `omni.ui 3.3.1` 专用窗口和现有视口。小型启动器拟用Python标准库 `tkinter/ttk` 与受控子进程管理：选案例、看运行状态、启动CPU或Kit、读历史证据；CPU和文本历史入口无需启动Kit。Kit打开后，主要审查与实体定位在其视口旁完成。启动器只保留必要摘要，不复制完整Kit面板。

`omni.ui.Window`支持停靠和窗口生命周期，官方说明UI内容不变时可复用绘制数据；这提供实现手段，不证明本项目开销已达标。[omni.ui 3.3.1 Window](https://docs.omniverse.nvidia.com/kit/docs/omni.ui/3.3.1/omni.ui/omni.ui.Window.html)

现有十相机可直接复用；官方 `frame_viewport_prims`支持按实体USD路径聚焦，但本项目自动定位仍待实现与相机/几何守卫验证。[viewport utility 2.1.0](https://docs.omniverse.nvidia.com/kit/docs/omni.kit.viewport.utility/2.1.0/omni.kit.viewport.utility/omni.kit.viewport.utility.frame_viewport_prims.html)

首个原型宜沿用现有Standalone脚本结构，不要求搭建新Kit应用。需要扩展化时参考6.1的CLI模板；旧UI Extension Template Generator自6.0起已弃用，不能推荐为新路线。[NVIDIA模板说明](https://docs.isaacsim.omniverse.nvidia.com/6.1.0/utilities/cli_extension_templates.html)、[弃用说明](https://docs.isaacsim.omniverse.nvidia.com/6.1.0/utilities/extension_templates_tutorial.html)

优点是直接复用已受测视口、相机和控件，新增依赖最少，贴合前置规划。取舍是启动器与Kit有两个窗口，CPU/历史使用小型界面，复杂证据表格的体验较受限。生产计算必须与界面刷新协调，不能把同步长计算放进点击回调，亦不能跨线程直接修改USD。Tk事件循环同样需要快速返回。[Python Tkinter线程模型](https://docs.python.org/3.12/library/tkinter.html#threading-model)

### B 独立PySide6桌面审查窗口

用 `PySide6 + Qt Widgets` 建立主窗口，统一案例、CPU/Kit运行、记录、实体列表和证据表格；Kit仍是独立进程及独立视口，桌面窗口通过受控消息请求定位。首版不尝试嵌入Kit窗口或新建三维渲染器。

官方发行目录已提供 `PySide6 6.12.0`（2026-10-08）的Windows x64 wheel，可作为选型后的验证候选；官方要求Python3.10+，建议独立虚拟环境。版本存在和满足声明范围不等于本机安装、打包或与Kit共存验证已通过。[官方发行目录](https://download.qt.io/official_releases/QtForPython/pyside6/)、[Qt for Python要求](https://doc.qt.io/qtforpython-6/gettingstarted.html#requirements)

拟用Qt信号及 `QProcess`观察进程生命周期，计算在后端进程执行。禁止在GUI线程阻塞等待；`terminate/kill`是进程终止手段，不能替代生产有序停止的请求、审计及持有事实保护。[QProcess文档](https://doc.qt.io/qtforpython-6/PySide6/QtCore/QProcess.html)

优点是无Kit时也有完整审查入口，表格、分栏和本地文件浏览方便，独立运行窗口更像专用工具。取舍是新增Qt绑定/二进制依赖、分发许可清单和桌面打包工作；GUI与Kit间仍有身份、断连和同步成本。拟将前端依赖隔离于自有前端环境或可选依赖组，不向Isaac安装注入Qt，也不改变CPU基础wheel的默认依赖。

### C 本地浏览器控制与审查页面

用 `FastAPI + Uvicorn` 提供本机薄服务，前端先用HTML/CSS及浏览器JavaScript模块，HTTP发送请求、获取带版本的状态与分页记录。首版用可配置的有限刷新频率；若原型证明推送必要，再选WebSocket并锁定相应依赖。单页控制/审查不必先引入React、Vite或Node构建链。

核验时官方列出 `FastAPI 0.143.0`（2026-10-08）和 `Uvicorn 0.54.0`（2026-09-24），作为后续原型验证候选；传递依赖和解释器兼容性须在选定后解算、锁定并验证，当前未安装。FastAPI提供HTTP/ASGI及WebSocket机制，连接断开处理仍需应用定义，框架不会自动提供运行幂等和重连同步。[FastAPI版本记录](https://fastapi.tiangolo.com/release-notes/)、[WebSocket说明](https://fastapi.tiangolo.com/advanced/websockets/)、[Uvicorn版本记录](https://uvicorn.dev/release-notes/)

拟显式绑定 `127.0.0.1`、单worker、关闭开发reload；后端生产进程仍只有一个事实所有者。即使本机页面，多个标签页也必须服从同一操作者控制锁；跨源/非本会话请求须拒绝，不因页面可打开而扩大为公网或多人控制。[Uvicorn配置](https://uvicorn.dev/settings/)

优点是布局、筛选和证据查看灵活，CPU及历史记录无需Kit。取舍是浏览器页面与Kit视口分离，增加本地服务生命周期、请求验证、网络连接状态及浏览器刷新/后台节流测试。首版只在Kit原视口显示三维；网页可显示有运行/时间标记的既有截图，不能把截图称为实时视频，不包含流媒体。

## 路线比较与推荐

下表是依据现有接口和官方能力作出的工程判断，复杂度及风险尚无原型测量或工期估算。

| 比较项 | A 原生面板加启动器 | B PySide6桌面 | C 本地浏览器 |
| --- | --- | --- | --- |
| 与既有规划符合度 | 最高，直接落实优先建议 | 原生交互不足时的合理路线 | 原生交互不足时的合理路线 |
| 日常操作 | Kit内看场景最连贯；CPU/历史用小入口 | 专用主窗口与Kit并排，信息管理一致 | 页面检索和分栏灵活，另切Kit看场景 |
| Kit/CPU/历史统一入口 | 启动器统一选案例/运行/证据；Kit承载主要视图 | 三者均在完整桌面主窗口选取和审查 | 三者均在同一本机页面选取和审查 |
| 视口复用 | 直接在同一Kit窗口旁操作 | 独立Kit视口，经桥接定位 | 独立Kit视口，经桥接定位 |
| 依赖及维护 | 复用既有Kit；启动器标准库，需维护两种轻UI | 增加Qt及前端环境/打包，隔离Kit | 增加ASGI服务及前端资源，维护连接/服务 |
| 新增前端开发复杂度 | 相对较低；生产显示/控制桥接仍不可省 | 中等；桌面与运行进程通信/文件索引 | 中等偏高；服务/请求/页面生命周期 |
| 性能主要风险 | Kit主循环饥饿、UI重建和记录解析占用 | GUI与生产争CPU/内存，IPC序列化 | 浏览器/服务/轮询争CPU，后台页面变陈旧 |
| 控制语义主要风险 | 场景/Kit时间轴按钮容易被误认为生产控制 | 关窗/结束进程容易被误认为有序停止 | 断连/刷新/多标签/重复请求易造成错觉 |

**推荐A**：当前任务的核心是审查既有Isaac场景并控制已批准的仿真运行，已有控件、相机和视口可复用；小型启动器补足CPU及历史入口，依赖增加最少。这个推荐包含启动器与薄运行层，并不意味着把所有模式塞进一个只能在Kit启动后使用的窗口。

如果日常工作主要是CPU试跑和大量历史记录查阅，B的完整独立主窗口更合适；若优先重视页面式信息布局和检索，且接受本机服务及分离视口，C更合适。三条路线都需要生产驱动适配，不存在仅换框架即可得到生产暂停、停止或回放的捷径。

## 信息布局与共同运行契约

以下只是信息布局示意，未制作原型。三种技术都可采用相同的层次；颜色、字体、卡片密度和明暗风格后续独立选择，当前选择不绑定审美方案。

```text
顶部：模式｜案例｜run_id/epoch｜源码/配置版本｜模拟时间｜数据年龄/连接状态
左侧：案例与历史记录      中部：Isaac视口或记录时间线      右侧：实体与等待/失败原因
底部：请求及后端确认｜事件摘要｜审计状态｜证据入口
控制区：默认观察；进入控制后才可启动/停止；未支持控制禁用并说明
```

四类入口明确标记：场景排演、轻量生产、真实Kit生产、历史记录回放。历史记录时间与播放游标分开，显示数据来源和原运行结束状态；缺少三维重建能力时只展示记录，禁止伪装实时。执行真值可在具名诊断视图显示，规划器继续只用已交付观察；前端不得向规划器传递隐藏情景或USD真值。

拟建薄运行层作为生命周期和请求的唯一管理者；其下现有生产驱动仍是唯一生产事实/派工所有者。前端只读取快照并提交白名单请求。相机定位可请求显示适配器操作视图，不直接修改生产USD实体或执行状态。

拟议消息至少绑定 `run_id/epoch/config_digest/source_version/request_id/revision/sequence`；时间保留仿真小时及单调墙钟来源，数据新鲜度来自状态心跳与最后后端消息而非UI刷新。新运行使用新身份和输出目录，旧证据保留，过期身份/修订拒绝；重复request_id与相同负载返回原回执，同ID不同负载拒绝。确认区分已收到、已生效、已拒绝，不能点完按钮即显示生效。

断连显示UNKNOWN及最后已知状态/时间；重连同步后端身份、能力、状态及已知请求结果，不自动补发旧命令。超时不等于拒绝或未执行。CPU长计算与Kit更新均需提供可观察心跳，UI陈旧必须如实显示。

| 操作 | 拟议首版语义与开放条件 |
| --- | --- |
| 启动 | 验证允许的案例/配置及单操作者，创建身份；只有后端初始化确认才进入运行态 |
| 有序停止 | 拟在合法事件边界形成终止检查点，保存未完成/在途及持有事实、双审计/日志并完成关闭回执；标记停止且订单未完成，不伪造完成或释放。原子计算可能延迟接收，须显示STOP_PENDING并实测响应 |
| 暂停与继续 | 当前只有控制器机制；运行中动作、仿真/人因时钟、反馈与恢复语义须先明确并贯通受测，未证明前禁用；不照搬Kit时间轴暂停 |
| 重置 | 结束旧运行后新建身份/epoch及新证据目录；不能清空原证据或复用旧消息。用户生产重置未证明前禁用，是否满足B3出口另裁定 |
| 订单取消 | 生产处置操作，只能走已批准通道并保留处置/资源规则；停止不能冒充取消，首版不开放任意取消编辑 |
| 关闭窗口 | 关闭显示或断开观察连接；不暗示生产已停止。只有实际停止确认和退出回执才显示已停止 |

首版限本机单操作者、默认观察、运行中参数只读。配置改变生成新配置和新运行；资格、碰撞、容量、所有权及调度核验保持。排演故障按钮不自动接入生产；任意脚本、拖物料改状态、批量实验、公网、多用户、真机、Web三维/流媒体不在首版范围。停止按钮不称工业急停。

## 选定后的制作与验收顺序

本轮“先选型后制作”覆盖原规划“原型后确定技术”的建议顺序。负责人选定路线后，先验证最小纵向原型：一例CPU、一例Kit、一个历史记录入口，显示同一套身份/时钟/状态并验证界面与驱动不互相阻塞。原型失败保留原因并回到选型评估，不自动切换或安装另一栈。下面均为未来动作，当前B1/B2/B3未开始。

1. **B1信息审查**：接入只读快照、案例/运行索引、版本/模式/时间/新鲜度、等待与失败原因、相机/实体定位和证据链接。区分审计未运行、通过、失败和记录不完整；验证观察隔离、陈旧状态、错误身份、缺失/损坏记录及取证不干预生产。负责人审阅信息是否真实、清楚、可查找。
2. **B2最小控制**：先固定薄契约及逐模式能力表，再在light和真实Kit生产贯通启动、有序停止和关闭回执；记录运行中持有事实及截尾语义。覆盖重复点击、相同ID不同负载、过期消息、断连前后确认丢失、重连不补发、非法模式/参数、并发操作者和中止期间请求。暂停/继续、重置逐项受测后开放，其余如实禁用；单元检查不能替代真实Kit用户路径。
