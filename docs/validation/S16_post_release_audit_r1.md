## F1 / P2：时间网格类型与正反映射不一致

位置：[domain.py:100](../../src/adaptive_hrc_scheduling/reference/domain.py#L100)、[checker.py:21](../../src/adaptive_hrc_scheduling/reference/checker.py#L21)、domain.py:237。

`tick_h`标注str，但validate只检查`Fraction(instance.tick_h)>0`。给原TINY_UNARY的tick_h设为数值0.1，输入验证接受、CP-SAT返回OPTIMAL/目标3；to_hours使用Fraction(float)得到二进制浮点的精确有理数，check_hours的quantize却使用Fraction(str(float))得到1/10，反映射报`off-grid time; explicit simplification required`。同一例用字符串"0.1"则完整反映射通过。布尔True也被接受、求解OPTIMAL，但小时检查报Invalid literal for Fraction。该反例未更改模型或检查器，也未关闭验证。

影响是输入已被认可且求解成功，却不能满足本步对应小时口径的出口；现有正向字符串网格测试没有覆盖数值/布尔形状。建议明确合法网格类型并在入口拒绝不合法形状，或对所有路径采用同一精确规范化，同时保持可序列化及摘要语义。不能在一侧使用二进制float有理值、另一侧使用十进制字符串。

## F2 / P2：资格数组被标量字符串拆开并错误放行

位置：domain.py:218—226，尤其`"qualifications": tuple(p["qualifications"])`。

角色要求原子资格ID W，人员正确数组只有["WELD"]时validate拒绝`role qualification`；仅把该数组改为错误形状字符串"WELD"，from_dict将其拆成["W","E","L","D"]，输入通过，CP-SAT为P1安排任务并返回OPTIMAL。普通资格ID之间没有前缀/字符包含授权关系，不能以此把一个资格变成四个资格。全部执行及核验均采用原发布实现，没有替换许可判断。

影响是JSON边界静默改变资格含义，不只是报错文字或容错问题。建议在tuple转换前检查容器/元素类型，保持原子ID，系统性检查其他会把字符串当序列的嵌套入口，并补合法数组/非法标量对照。既有具名角色、HR禁用及工业UNKNOWN边界保持。

## F3 / P2：EDD漏掉接收任务交期，且两个标签共用同一策略

位置：baselines.py:38—55。due只从product.ready初始化并向其前序传播，store/receive没有产品due，未初始化的传播还会以horizon夹小较晚交期。任务优先级除了SPT之外均走同一分支，替代模式也始终按(duration,cost,id)排序，因此EDD与FASTEST_MODE在非预算截断情形下策略逻辑相同。

反例为两个输出位、FG容量2、两独立搬运设备、两具名合格操作者以及共享接收资源。两产品均可在2开始接收，A_LONG交期10、Z_SHORT交期3，任务各1tick、窗口6。现行EDD先按ID安排A_LONG于2—3接收，再安排Z_SHORT于3—4接收，独立目标5；手排早交期Z_SHORT先2—3、A_LONG后3—4，独立检查通过、目标4，CP-SAT亦证明最优4。这项差异来自未传播到接收任务的交期，不是不同可行域、隐藏真值、不同容量或物流费用。

EDD本来不保证最优，但本例要指出的是它没有按本模型的接收交期执行所称EDD规则。建议先明确产品全部相关任务的交期语义及正向下游标记，再处理次序；同时明确EDD/FASTEST_MODE是不同定义还是别名。允许选择别名，但不能据两个标签解释为两种独立机制覆盖。原七例21条标签运行/18条可行计划是实际计数，不能据此推导有三种不同策略。
